## 一、内存组织（Memory Organization）

### 1.1 数据 vs 指令

- 计算机使用**指针/寄存器（Program Counter, PC）**来指向下一条要执行的指令
- 硬件获取PC指向地址的字节，作为指令执行（如 jump, goto）
- **关键问题**：代码和数据存储在**同一块内存**中 → 攻击者可能通过覆写数据来改变代码执行

> 📍 *Slide 4-5*

### 1.2 内存布局

```
      高地址
   ┌──────────┐
   │  Stack   │ ← 栈：存储子任务的调用与返回数据（函数调用栈）
   │    ↓     │    先进后出（LIFO）
   │    ↑     │
   │  Heap    │ ← 堆：动态内存空间（编译时大小未知的数据）
   └──────────┘
   │  Code    │ ← 指令从低地址向上移动
   └──────────┘
      低地址
```

- **堆（Heap）**：存储动态产生的数据
- **栈（Stack）**：存储子任务的调用与返回数据
- 堆和栈**朝彼此增长**，攻击者可以预测（或操纵）它们在某一点碰撞

## 二、栈与过程调用（The Stack）

### 2.1 栈的工作原理

- 栈是程序间进行数据交换的**关键数据结构**——**先进后出（LIFO）**
- 当过程A调用过程B时：A将**返回地址**（PC当前值）压入栈
- 当B退出时：从栈中弹出返回地址，继续从该地址执行

> 📍 *Slide 10*

### 2.2 栈被破坏的后果

> 如果攻击者能够**覆写（overwrite）程序计数器**，就能重定向程序执行路径。

覆写内存以劫持执行的三种方式：
| 方式 | 说明 |
|------|------|
| 覆写栈中存储的PC | 改变返回地址 |
| 覆写低内存中的部分代码 | 替换为新指令 |
| 覆写PC和栈中数据 | 使PC指向栈（栈中已有攻击者注入的代码） |

> 📍 *Slide 12, 14*

## 三、缓冲区溢出（Buffer Overflow）⭐⭐⭐

### 3.1 定义

> 当数据写入**超出为其分配的空间**时发生，如向9字节数组写入第10个字节。

在一个典型的可溢出漏洞中：
- 攻击者的输入预期应进入**数据区**
- 但实际允许覆盖了存放**可执行代码**的内存

攻击者的关键技巧：
1. **找到**缓冲区溢出机会，使被覆盖的内存被执行
2. **找到**正确的代码来输入

> 📍 *Slide 6*

### 3.2 溢出的具体示例

```c
char sample[10];
int i = 0;
for (i = 0; i <= 9; i++)
    sample[i] = 'A';
sample[10] = 'B';   // 越界！写到了数组范围之外
```

> 📍 *Slide 7*

### 3.3 缓冲区溢出的危害

缓冲区溢出可能覆盖：
| 覆盖对象 | 后果 |
|----------|------|
| 程序的另一部分**数据** | 数据损坏 |
| 程序中的**指令** | 攻击者获得**该程序的执行权限** |
| 属于**其他程序**的数据或代码 | 跨进程破坏 |
| 属于**操作系统**的数据或代码 | 攻击者获得**OS的执行权限**（rootkit） |

> 📍 *Slide 15*

### 3.4 缓冲区溢出对策

| 对策 | 说明 |
|------|------|
| **不超出开辟空间界限** | 写之前检查长度 |
| **确认数组下标在限制范围内** | 但实践中难以全面检查 |
| **检查边界条件代码** | 防止off-by-one错误（±1错误） |
| **限制输入字符数** | 白名单输入验证 |
| **限制程序权限** | 最小权限原则 |
| **语言级保护** | 许多语言有溢出保护（如Java） |
| **代码分析器** | 可识别许多溢出漏洞 |
| **栈金丝雀（Canary Values）** | 栈中随机值，检测是否被修改 ⭐ |
| **Stack Guard** | 插入金丝雀值，若被重写则在返回前发出错误信号 |

> 📍 *Slide 16*

## 四、不完整仲裁（Incomplete Mediation）

### 4.1 定义

**Mediation（仲裁/验证）**：验证主体是否被**授权**对客体执行操作。

**Incomplete Mediation**：验证不完整，存在可被绕过的验证缺口。

### 4.2 预防措施

- 验证**所有**输入
- 限制用户对敏感数据和功能的访问
- 使用**参考监视器（Reference Monitor）**实现完整仲裁

> 📍 *Slide 20*

### 4.3 检查时刻到使用时刻（TOCTOU）漏洞

> 在"检查"和"使用"之间存在时间差，攻击者在此期间进行**偷梁换柱**（Bait and Switch）。

例：检查文件权限时合法 → 使用文件时已被替换为恶意文件。

> 📍 *Slide 21*

## 五、竞态条件（Race Conditions）⭐

### 5.1 定义

多进程/线程在**未同步**情况下访问共享OS资源，导致结果**不可预测**。攻击者可利用时间窗口（如进程切换间隙）提升权限或破坏数据。

### 5.2 防护

使用**锁定机制（Locking）**，确保资源在同一时间只被一个进程访问。

> 📍 *Slide 22-23*

## 六、其他编程疏忽

课件列出了常见编程错误：

| 疏忽类型 | 说明 |
|----------|------|
| **未记录的后门（Backdoors）** | 开发时留下的隐蔽访问点 |
| **Off-by-one 错误** | 如 `i<=n` 还是 `i<n`？ |
| **整数溢出（Integer overflow）** | 数值超出整数类型范围 |
| **未终止的空终止字符串** | 字符串无 `\0` 结尾 |
| **参数长度/类型/数量错误** | 函数调用参数不匹配 |
| **不安全的工具库** | 使用有漏洞的第三方库 |

## 七、恶意软件（Malware）⭐⭐⭐

### 7.1 基本定义

| 术语 | 课件定义 |
|------|----------|
| **Malware（恶意软件）** | 由恶意代理人植入的程序，旨在造成非预期或有害的效果 |
| **Virus（病毒）** | 能**自我复制**并通过修改其他非恶意程序**传播恶意代码**的程序 |
| **Worm（蠕虫）** | 通过网络**传播自身副本**的程序 |
| **Trojan Horse（木马）** | 除声明功能外，还有第二重**隐蔽的恶意效果**的代码 |

> 📍 *Slide 25*

> 📖 特洛伊战争背景（课件详述）：公元前12世纪希腊联军用木马计攻陷特洛伊——木马外表看着有用，内藏杀机。

### 7.2 恶意软件的传播方式

| 方式 | 说明 |
|------|------|
| 安装程序（Setup/Installer） | 伪装成正常安装包 |
| 附件文件（Attached file） | 邮件附件带毒 |
| 文档病毒（Document viruses） | 利用文档宏 |
| 自动运行（Autorun） | 利用自动播放 |
| 附加型病毒（Appended viruses） | 附着在合法程序上 |
| 环绕型病毒（Viruses that surround） | 包裹原程序 |
| 集成/替代型病毒 | 完全替换原程序 |

> 📍 *Slide 34*

### 7.3 恶意软件的激活方式

| 激活方式 | 说明 |
|----------|------|
| 一次性执行（植入时） | 安装即触发 |
| 引导扇区病毒（Boot sector） | 开机时激活 |
| 内存驻留病毒（Memory-resident） | 常驻内存 |
| 应用程序文件激活 | 打开应用时触发 |
| 代码库激活 | 调用库函数时触发 |

> 📍 *Slide 35*

### 7.4 恶意软件的危害

**对用户和系统的危害**：
- 向用户联系人发邮件
- 删除或加密文件（勒索病毒）
- 修改系统信息（如Windows注册表）
- 窃取敏感信息（如密码）
- 附加到关键系统文件
- 在多个互补位置隐藏副本

**对世界的危害**：
- 感染数百万系统，以**几何速度**增长
- 受感染系统成为新感染的**集结地**

> 📍 *Slide 33*

### 7.5 用户防范对策

| 对策 | 说明 |
|------|------|
| 使用可靠来源软件 | 不从不明网站下载 |
| 隔离环境测试 | 在沙箱中先运行 |
| 确认安全再打开附件 | 附件要核实来源 |
| 将每个网站视为潜在有害 | 保持警惕 |
| 创建和维护备份 | 防勒索最后防线 |

> 📍 *Slide 37*

## 八、病毒检测（Virus Detection）

### 8.1 检测方式

- 病毒扫描器在程序文件和内存中寻找恶意代码感染的**签名（Signature）**标记
- 传统病毒扫描器只能检测约 **45%** 的新恶意软件

**检测机制**：
| 机制 | 说明 |
|------|------|
| 文件/内存中的**已知字符串模式** | 特征码匹配 |
| **执行模式** | 行为分析 |
| **存储模式** | 存储特征检测 |

> 📍 *Slide 38-39*

## 九、开发者的安全编码实践

### 9.1 模块化代码原则

每个代码模块应该：**单一目的（Single-purpose）、小（Small）、简单（Simple）、独立（Independent）**

| 原则 | 说明 |
|------|------|
| **封装（Encapsulation）** | 隐藏内部实现细节 |
| **信息隐藏（Information hiding）** | 不暴露内部状态 |
| **相互怀疑（Mutual Suspicion）** | 模块之间不信任彼此 |
| **隔离（Confinement）** | 将失败限制在一定范围 |
| **遗传多样性（Genetic diversity）** | 避免同一个bug影响所有模块 |

> 📍 *Slide 40*

### 9.2 代码测试类型

| 测试类型 | 说明 |
|----------|------|
| 单元测试（Unit testing） | 测试单个模块 |
| 集成测试（Integration testing） | 测试模块交互 |
| 功能测试（Function testing） | 测试功能正确性 |
| 性能测试（Performance testing） | 测试性能指标 |
| 验收测试（Acceptance testing） | 用户验收 |
| 安装测试（Installation testing） | 安装过程测试 |
| 回归测试（Regression testing） | 防止旧bug复现 |
| **渗透测试（Penetration testing）** | 模拟攻击测试安全 |

> 📍 *Slide 41*

### 9.3 安全设计原则（Design Principles for Security）⭐⭐⭐

| 原则 | 英文 | 说明 |
|------|------|------|
| **最小权限** | Least privilege | 只授予完成任务所需的最小权限 |
| **机制经济性** | Economy of mechanism | 机制越简单越容易保证安全 |
| **开放设计** | Open design | 安全性不依赖设计的保密 |
| **完整仲裁** | Complete mediation | 每次访问都需验证 |
| **基于权限** | Permission based | 默认拒绝，显式授权 |
| **权限分离** | Separation of privilege | 关键操作需要多重授权 |
| **最小公共机制** | Least common mechanism | 减少共享机制 |
| **易用性** | Ease of use | 安全措施要易于正确使用 |

> 📍 *Slide 42*

### 9.4 好的实践 vs 坏的实践

| ✅ 好的实践（Good） | ❌ 坏的实践（Bad） |
|---------------------|---------------------|
| 程序正确性证明（可能时） | **Penetrate-and-patch**（攻破了再补） |
| 防御式编程（Defensive programming） | **Security by obscurity**（依赖算法/设计保密） |
| 契约式设计（Design by contract） | — |

## 十、本章总结

1. 缓冲区溢出攻击利用**代码和数据存储在同一内存**的事实，恶意修改执行中的程序
2. 程序还有off-by-one错误、不完整仲裁、竞态条件等漏洞
3. 恶意软件可根据资源使用、感染向量和载荷产生各种有害效果
4. 开发者可使用多种技术编写和测试安全代码

## 名词解释速记

| 术语 | 一句话定义 |
|------|-----------|
| Buffer Overflow | 写入数据超出分配空间，覆盖相邻内存 |
| Stack Canary | 栈中的随机值，检测缓冲区是否被溢出修改 |
| Race Condition | 多进程未同步访问共享资源导致的不可预测行为 |
| Incomplete Mediation | 验证不完整，攻击者可绕过访问控制 |
| TOCTOU | 检查后到使用前的时间窗口被利用进行替换 |
| Virus | 自我复制，需宿主程序传播 |
| Worm | 独立传播，通过网络自动扩散 |
| Trojan Horse | 伪装合法软件，内含恶意功能 |
