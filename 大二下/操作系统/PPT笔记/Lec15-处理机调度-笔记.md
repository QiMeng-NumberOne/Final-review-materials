## 1. 处理机调度概念

### 1.1 什么是处理机调度

> **调度程序(Scheduler)**：从**就绪队列**中挑选下一个占用 CPU 运行的进程的内核函数。

```
CPU 资源的时分复用：

  进程A运行 → 中断/时间片到 → 调度程序 → 选择进程B → 切换上下文 → 进程B运行
  ────────                  ────────               ────────
  ① 保存A的上下文            ② 挑选就绪进程          ③ 恢复B的上下文
    到A的PCB                   依据调度策略            从B的PCB
```

### 1.2 调度时机 — 什么时候进行调度？

```
         创建 ──→ 就绪
                   │
                   ▼
         ┌──────────────────────────┐
         │        就绪(Ready)        │
         └──────┬──────────┬────────┘
                │ 被调度   │
                ▼          │ 时间片完     ← 调度时机③（可抢占才有）
         ┌──────────┐     │
         │ 运行      │─────┘
         │ (Running)│
         └────┬─────┘
              │ 等待事件               ← 调度时机①（主动放弃CPU）
              ▼
         ┌──────────────┐
         │ 等待(Blocked) │
         └───┬──────────┘
             │ 事件发生               ← 调度时机②（被唤醒，可能抢占）
             └──────→ 回到 就绪
              │
              ▼
          结束(Exit)                ← 调度时机④（进程终结）
```

| 系统类型 | 调度时机 | 特点 |
|------|------|------|
| **非抢占系统** | 只有①②④ | 进程主动放弃 CPU 时才调度（如早期 Windows 3.1） |
| **可抢占系统** | ①②③④ | 时间片到/中断/更高优先级就绪 都可触发调度（现代 OS） |

**内核运行调度程序的条件**：

```
① 进程从运行状态切换到等待状态（主动放弃）
② 进程被终结了
③ 进程时间片用完（可抢占）
④ 进程从等待切换到就绪（可抢占）
⑤ 中断请求被服务例程响应完成时（可抢占，当前进程被抢占）
```

### 1.3 进程的 CPU-I/O 交替模式

```
进程执行 = CPU计算(CPU burst) + I/O操作(I/O burst) 反复交替

   CPU计算     I/O等     CPU计算    I/O等    CPU计算     I/O等
  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────────┐  ┌──────┐
  │load   │  │等磁盘  │  │store  │  │等键盘  │  │read file  │  │等网络 │
  │add    │  │      │  │inc    │  │      │  │write file│  │      │
  └──────┘  └──────┘  └──────┘  └──────┘  └──────────┘  └──────┘
  ← CPU突发短 →      ← CPU突发短 →     ← CPU突发长 →

CPU密集型进程：CPU突发长，I/O少（科学计算、视频编码）
I/O密集型进程：CPU突发短，I/O频繁（交互程序、Web服务器）

调度策略要兼顾两者：
  I/O密集型应优先 → 快速响应 → 尽快开始下一轮I/O
  CPU密集型用剩余时间 → 后台慢慢算
```

## 2. 调度准则

### 2.1 五大评价指标

```
周转时间 (Turnaround Time)
  = 进程从创建到结束的总时间

等待时间 (Waiting Time)
  = 进程在就绪队列中的总时间

响应时间 (Response Time)
  = 从用户提交请求到系统第一次响应的时间

吞吐量 (Throughput)
  = 单位时间内完成的进程数量

CPU利用率 (CPU Utilization)
  = CPU 处于忙状态的时间百分比
```

### 2.2 吞吐量 vs 响应时间 — 水管理论（PPT）

```
     高吞吐量 (Throughput)              低延迟 (Latency)
   给游泳池充水，希望水管粗             喝水，希望一开水龙头就有
   恨不得水柱像洪水一样涌出来             不能有任何等待
   
   对应：批处理系统                     对应：交互系统
   目标：最大化单位时间完成的任务数        目标：用户操作马上有反馈

这两个目标是 独立的、矛盾的。
调度算法需要在两者之间做权衡。
```

### 2.3 响应时间目标

```
交互系统：
  及时处理用户输入，尽快反馈
  低延迟 → 改善用户体验
  如果鼠标移动后光标没动 → 用户可能重启电脑！

  减少响应时间的平均波动很重要：
    可预测性 > 低平均值
    用户能忍受"有点慢"，但不能忍受"一会快一会卡"
```

### 2.4 公平性目标

```
公平的定义不唯一：
  ① 每个进程的等待时间相同？
  ② 每个进程占用相同的 CPU 时间？

更深层的问题：
  A用户开2个进程，B用户开8个进程
  按进程平均分配 → B拿走4倍于A的CPU
  → 这"公平"吗？
  → 需要按 用户 而不是按 进程 分配 → 公平共享调度(FSS)
```

## 3. 调度算法

### 3.1 先来先服务（FCFS）

**规则**：按进入就绪队列的先后顺序执行，先到的先跑。**非抢占**。

#### 示例（PPT）

```
3个进程：P1执行12, P2执行3, P3执行3

到达顺序 P1, P2, P3：
  P1 ████████████│P2 ███│P3 ███│
  0             12     15     18
  周转时间 = (12 + 15 + 18) / 3 = 15
  等待时间：P1=0, P2=12, P3=15  Avg=9

到达顺序 P2, P3, P1：
  P2 ███│P3 ███│P1 ████████████│
  0     3      6              18
  周转时间 = (3 + 6 + 18) / 3 = 9  ← 同样的进程，换了顺序结果大不同！
  等待时间：P2=0, P3=3, P1=6   Avg=3
```

| 优点 | 缺点 |
|------|------|
| 简单 | 平均等待时间波动大（依赖到达顺序） |
| | 短进程排在长进程后面 → 护航效应 |
| | CPU密集 → I/O密集全等在后面 → 资源利用率低 |

---

### 3.2 短进程优先（SPN / SJF / SRT）

**SPN/SJF**：选择**预期执行时间最短**的进程。**非抢占**。

```
就绪队列按预期执行时间排序（队头=最短）：
  队头 ← Pw(c=9) ← Px(c=12) ← Py(c=34) ← Pz(c=62) ← 队尾

⭐ SPN 的 平均周转时间是最优的
```

**SRT（Shortest Remaining Time）— 抢占版**：

```
新进程到达时：
  如果新进程的 剩余执行时间 < 当前运行进程的剩余执行时间
  → 抢占！
```

#### 执行时间预估（PPT 公式）

```
问题：CPU执行时间无法预知 → 用历史执行时间预测未来

  τn+1 = α·tn + (1-α)·τn

     tn = 第n次 实际 CPU执行时间
     τn = 第n次 预估 CPU执行时间
     0 ≤ α ≤ 1

  α=1   → τn+1 = tn        → 只看最近一次
  α=0   → τn+1 = τn        → 只看初始估计
  α=0.5 → 最近和历史的折衷    → 指数加权平均

示例（PPT 数据）：
  实际(ti):  6   4   6   4   13   13   13   ...
  预估(τi): 10   8   6   6    5    9   11   12   ...
  新的预估值逐步跟踪实际值变化
```

| 优点 | 缺点 |
|------|------|
| 平均周转时间最优（SPJ最小化） | **需要预测未来** |
| | 可能导致**饥饿**：长进程永远轮不到 |
| | 连续的短进程流 → 长进程永无天日 |

---

### 3.3 最高响应比优先（HRRN）

**规则**：选择**响应比 R 最高**的进程。**非抢占**。

```
  R = (w + s) / s = 1 + w/s

  w = 等待时间 (已经在就绪队列中等了多久)
  s = 执行时间 (预期还要跑多久)

设计思路：
  短进程 → s小 → R大 → 优先（保留了SPN的优点）
  长进程等久了 → w变大 → R变大 → 最终也能被调度（解决了饥饿问题！）

  当等待时间足够长 → 长进程的R会超过新短进程的R
  → 长进程不会被无限期推迟
```

| 优点 | 缺点 |
|------|------|
| 在SPN基础上改进，**防止饥饿** | 不可抢占 |
| 关注进程的等待时间 | 需要预估执行时间 |

---

### 3.4 时间片轮转（RR）

**规则**：每个进程分配**时间片 q**，时间片完按 FCFS 切换到下一个。**可抢占**。

```
      时间片q
  Pa ─────────│ 时间片到！
              │
  Pb ─────────│ 时间片到！
              │
  Pc ─────────│ ...

每隔 (n-1) 个时间片，一个进程能跑一个时间片。
```

#### PPT 完整追踪示例（RR q=20）

```
进程：P1=53, P2=8, P3=68, P4=24, q=20

甘特图：
 P1███│P2│P3████████│P4████████│P1████████│P3████████│P4│P1██│P3████████│
 0   20  28         48         68         88        108 112 125       145 153

P1 等待时间 = (68-20) + (112-88) = 72
P2 等待时间 = 20
P3 等待时间 = (28-0) + (88-48) + (125-108) = 85
P4 等待时间 = (48-0) + (108-68) = 88
平均等待时间 = (72 + 20 + 85 + 88) / 4 = 66.25
```

#### 时间片大小的影响（PPT 数据表）

```
进程：P1=53, P2=8, P3=68, P4=24

┌──────────┬─────┬─────┬─────┬───────┬──────┬──────┐
│  q=      │  1  │  5  │  8  │  10   │  20  │FCFS  │
├──────────┼─────┼─────┼─────┼───────┼──────┼──────┤
│ P1等待    │ 84  │ 82  │ 80  │ 82   │ 72  │ 0    │
│ P2等待    │ 22  │ 20  │  8  │ 10   │ 20  │ 53   │
│ P3等待    │ 85  │ 85  │ 85  │ 85   │ 85  │ 61   │
│ P4等待    │ 57  │ 61  │ 68  │ 88   │ 88  │ 129  │
│ Avg等待   │83.5 │57.25│61.25│66.25 │66.25│60.75 │
└──────────┴─────┴─────┴─────┴───────┴──────┴──────┘

观察：
  FCFS → P2等53,P4等129 极不公平
  q=1  → Avg=83.5 最差（切换开销太大）
  q=5  → Avg=57.25 最佳（平衡了响应和开销）
  q→大 → 趋近 FCFS
```

#### 时间片长度选择

```
时间片太大 → 退化成 FCFS → 等待时间过长 → 交互体验差
时间片太小 → 上下文切换太频繁 → 系统吞吐量下降

经验规则：上下文切换开销 ≤ 总时间的 1%
  切换开销 ~0.1ms → 时间片 ≥ 10ms
  典型值：10ms ~ 100ms
```

| 优点 | 缺点 |
|------|------|
| 公平、响应快 | 额外上下文切换开销 |
| 交互系统的基础 | 平均等待时间可能较差 |

### 3.5 多级队列（MQ）

**规则**：就绪队列分成**多个独立子队列**，每个有自己的调度策略。

```
  ┌─────────────────────────────┐
  │ 前台队列（交互式进程）         │ → RR 调度（响应快）
  │ 高优先级                     │
  ├─────────────────────────────┤
  │ 后台队列（批处理进程）         │ → FCFS 调度（吞吐量高）
  │ 低优先级                     │
  └─────────────────────────────┘

队列间的调度：
  ① 固定优先级：先处理完前台再处理后 → 后台可能饥饿
  ② 时间片分配：80% CPU给前台，20%给后台
```

---

### 3.6 多级反馈队列（MLFQ）

> ⭐ **现代操作系统的核心调度算法**（Windows、Linux 都基于此思想）。

**规则**：进程可在不同队列间**动态移动**。

```
          新进程进入
              │
              ▼
  ┌─────────────────────┐
  │ 队列1（最高优先级）     │ q = t0          ← 时间片最小
  │      ↓ 没完成        │
  ├─────────────────────┤
  │ 队列2               │ q = 2×t0
  │      ↓ 没完成        │
  ├─────────────────────┤
  │ 队列3               │ q = 4×t0
  │      ↓ 没完成        │
  ├─────────────────────┤
  │ 队列n（最低优先级）    │ q = 2^(n-1)×t0  ← 时间片最大
  └─────────────────────┘

规则：
  ● 新进程进入最高优先级队列
  ● 在当前队列时间片内没完成 → 降到下一级
  ● 时间片随级别降低而 翻倍增大
  ● 低优先级队列只在高优先级空时才被调度
  ● 被抢占的进程回到原队列

结果（自动适应，无需预知执行时间）：
  ● I/O密集型 → CPU突发短 → 时间片内完成 → 留在高优先级 → 响应快 ✅
  ● CPU密集型 → CPU突发长 → 用完时间片 → 自然沉底 → 在后台慢慢算
  → 不需要像 SPN 那样预测执行时间！
```

| 优点 | 缺点 |
|------|------|
| 多种算法的**集成** | 复杂度较高 |
| 自动区分 I/O密集型 和 CPU密集型 | 参数调优需要经验 |
| 兼顾 短进程优先 和 长进程不饿死 | |

### 3.7 公平共享调度（FSS）

**规则**：按**用户/用户组**分配 CPU 资源，而不是按进程。

```
             系统资源
           ／    |    ＼
        U1(40%) U2(30%) U3(20%) ... Un(10%)
        ／＼     ／＼
      P1  P2   P3  P4 ...

A用户2个进程 → 共享40%的CPU
B用户8个进程 → 共享30%的CPU

核心思想：
  ● 不重要组无法垄断资源
  ● 未使用的资源按比例重新分配
  ● 未达资源使用目标的组 → 提高优先级
```

| 优点 | 缺点 |
|------|------|
| **公平是第一要素** | 实现复杂 |

---

### 3.8 算法总结对比

| 算法 | 抢占 | 优点 | 缺点 |
|------|:---:|------|------|
| **FCFS** | ✗ | 简单 | 护航效应，短进程等长进程 |
| **SPN/SJF** | ✗ | **平均周转时间最小** | 需预测，长进程饥饿 |
| **SRT** | ✓ | SPN抢占改进 | 同上 |
| **HRRN** | ✗ | SPN改进，**防饥饿** | 需预估执行时间 |
| **RR** | ✓ | 公平，响应快 | 额外切换开销 |
| **MQ** | ✓ | 不同策略混合 | 队列间调度需设计 |
| **MLFQ** | ✓ | **多种算法集成**，自适应 | 复杂度高 |
| **FSS** | ✓ | 按用户公平 | 实现复杂 |

## 4. 实时调度

### 4.1 实时操作系统

```
定义：正确性依赖于其 时间 和 功能 两方面

关键特性：
  ● 时间约束的及时性（必须满足 deadline）
  ● 速度和平均性能 相对不重要
  ● 时间约束的可预测性 最重要

性能指标：时间约束的满足程度，不是吞吐量
```

### 4.2 硬时限 vs 软时限

| | 硬时限 (Hard Deadline) | 软时限 (Soft Deadline) |
|------|------|------|
| **错过后果** | **灾难性**（飞机坠毁、刹车失灵） | 降低服务质量，可容忍 |
| **验证要求** | 必须证明**最坏情况**都能满足 | 尽力而为 |
| **典型场景** | 航空控制、汽车ABS、医疗设备 | 视频播放、游戏、VoIP |

### 4.3 强实时 vs 弱实时操作系统

```
强实时：必须在指定时间内完成重要任务
弱实时：重要进程有高优先级，尽量但不保证完成
```

### 4.4 周期实时任务

```
周期实时任务：有规律地重复

  周期 p = 任务请求时间间隔 (0 < p)
  执行时间 e = 最大执行时间 (0 < e < p)
  使用率 U = e / p

  ┌─┐    ┌─┐    ┌─┐    ┌─┐    ┌─┐
  │ │    │ │    │ │    │ │    │ │    ...
  └─┘    └─┘    └─┘    └─┘    └─┘
  ← p →  ← p →  ← p →  ← p →
```

### 4.5 可调度性

> 可调度 = 实时操作系统**能够满足所有任务时限要求**。

```
需要确定任务执行顺序：
  ├── 静态优先级调度：RM（优先级固定，周期越短越高）
  └── 动态优先级调度：EDF（优先级动态变化，截止越早越高）
```

### 4.6 速率单调调度（RM — Rate Monotonic）

```
规则：周期越短 → 优先级越高
      按周期安排优先级，执行周期最短的任务

原理：
  周期短 = 更频繁地需要执行
        = 更紧迫 → 更高优先级
```

### 4.7 最早截止时间优先（EDF — Earliest Deadline First）

```
规则：截止时间越早 → 优先级越高
      每次调度时重新计算谁最早截止

特点：动态优先级（会在运行过程中变化）
```

## 5. 多处理器调度

### 5.1 对称多处理器（SMP）

```
多个相同的处理器，每个运行自己的调度程序，处理机间可负载共享

    逻辑CPU    逻辑CPU    逻辑CPU    逻辑CPU
       ↕          ↕          ↕          ↕
    物理CPU    物理CPU    物理CPU    物理CPU
       └──────────┴──────────┴──────────┘
                    系统总线
                    
调度程序访问共享资源需要同步（避免两个CPU同时操作同一队列）
```

### 5.2 静态分配 vs 动态分配

| | 静态分配 | 动态分配 |
|------|------|------|
| **方式** | 进程固定在**一个**处理器 | 进程可分配到**任意**空闲处理器 |
| **就绪队列** | 每个处理器**独立**一个队列 | 所有处理器**共享**一个全局队列 |
| **优点** | 调度开销**小** | **负载均衡** |
| **缺点** | 各处理器忙闲不均 | 调度开销大，队列需同步锁 |

## 6. 优先级反置

### 6.1 什么是优先级反置

> 高优先级进程长时间等待低优先级进程所占用的资源。

#### PPT 经典场景

```
T1 (优先级40, 低)
T2 (优先级50, 高)
T3 (优先级46, 中)

时间线：
  T1 运行，占用资源 L1（进入临界区）
    → T2 就绪，优先级50 > 40 → 抢占T1，T2运行
    → T2 尝试获取 L1 → L1 被 T1 持有 → T2 阻塞！
    → T1 恢复运行（T2在等它释放L1）
    → T3 就绪，优先级46 > 40 → 抢占T1！T3运行
    → T3 长时间运行...
    → T2(优先级50！) 在等 T1(优先级40)，T1 又被 T3(优先级46) 阻塞
    → T2 实际被降到优先级46！

  T2 是最高优先级的，却在等中低优先级的 T3！
```

### 6.2 优先级继承（Priority Inheritance）

```
T1 占用 L1：
  T2 申请 L1 → 被阻塞
  → T1 暂时 继承 T2 的高优先级(50)
  → T3(46) 无法再抢占 T1
  → T1 快速完成临界区 → 释放 L1 → 回到原优先级(40)
  → T2(50) 获得 L1 → 顺利运行

只在 被阻塞 时临时提升占用者优先级
```

### 6.3 优先级天花板协议（Priority Ceiling Protocol）

```
资源 L1 的"天花板优先级" = 所有可能申请 L1 的进程中 最高的 那个优先级

不管是否发生等待，占用 L1 的进程 立即 提升到天花板优先级。

效果：
  占用关键资源的进程 → 立即获得高优先级
  → 快速执行完临界区 → 释放资源
  → 高优先级进程不会被长时间阻塞

继承 vs 天花板：
  继承：等阻塞了再升
  天花板：提前升，不等阻塞发生
```

## 7. ucore 调度框架

### 7.1 调度算法统一接口

```c
struct sched_class {
    const char *name;                    // 算法名称（如 "RR", "Stride"）
    void (*init)(struct run_queue *rq);  // 初始化就绪队列
    void (*enqueue)(struct run_queue *rq, struct proc_struct *proc);  // 入队
    void (*dequeue)(struct run_queue *rq, struct proc_struct *proc);  // 出队
    struct proc_struct *(*pick_next)(struct run_queue *rq);  // 选下一个运行
    void (*proc_tick)(struct run_queue *rq, struct proc_struct *proc); // 时间片更新
};

// 通过函数指针实现多态 → 不同调度策略只需实现这一套接口
```

### 7.2 调度队列结构

```c
struct run_queue {
    list_entry_t run_list;   // 就绪进程链表
    unsigned int proc_num;   // 当前就绪进程数
    int max_time_slice;      // 最大时间片（RR中每个进程的时间配额）
    list_entry_t rq_link;    // 队列链接（用于多队列算法）
};
```

### 7.3 ucore 线程状态

```
UNINIT   → 未初始化（刚创建）
RUNNABLE → 就绪（等待CPU）
RUNNING  → 运行中
SLEEPING → 等待/阻塞（等待事件）
ZOMBIE   → 僵尸（已结束，等父进程回收）

状态流转：
  alloc_proc → UNINIT
  proc_init → RUNNABLE
  wakeup_proc → RUNNABLE
  schedule → RUNNING
  do_sleep → SLEEPING
  do_exit → ZOMBIE
```

### 7.4 调度时机与进程切换（PPT 图解）

```
进程1用户态 ──trap(中断)──→ 进程1内核态
                                │
                          ① 保存trapframe
                          ② 处理中断/trap
                          ③ 调用schedule()
                                │
                                ▼
                          ④ 恢复trapframe
                                │
进程2内核态 ──iret──→ 进程2用户态（运行中）
                                │
                           ... 中断/trap ...
                                │
                          ⑤ 保存trapframe
                          ⑥ 处理 + schedule()
                                │
                                ▼
                          ⑦ 恢复trapframe
                                │
回到进程1用户态继续运行
```

## 8. FAQ

### Q1：调度发生在什么时候？

非抢占系统：进程主动放弃 CPU 时（等待I/O、结束）。
可抢占系统：以上 + 时间片到 + 更高优先级进程就绪 + 中断完成。

### Q2：SPN 为什么平均周转时间最优？

短进程排前面 → 它们快速完成 → 不会因为等长进程而浪费时间。类似银行柜台——先处理快的人，整体平均等待时间最短。（理论可证：短作业优先最小化平均周转时间）

### Q3：MLFQ 为什么不需要预知执行时间？

靠"试用期"机制：新进程给短时间片（高优先级），能跑完说明是短进程→留高层；跑不完说明是长进程→自动降级。用"行为"区分，不用"预测"。

### Q4：RR 时间片设多大合适？

经验值 10~100ms，保证上下文切换开销（~0.1ms）不超过总时间 1%。太小→切换太多吞吐量差，太大→退化成FCFS。

### Q5：优先级反置怎么解决？

- **优先级继承**：低优先级进程阻塞了高优先级时，临时继承高的优先级
- **天花板协议**：占用关键资源的进程，立即提升到该资源可能被申请的最高优先级

### Q6：硬时限和软时限的区别？

硬时限错过 = 灾难（飞机控制系统），必须证明最坏情况都能满足。软时限错过 = 体验降级（视频播放偶尔卡顿），尽力而为。
