## 1. 死锁概念

> 死锁：两个或更多线程在执行中，**永远相互等待**只能由其他进程引发的事件。

```
死锁类比（PPT 单向桥）：
  
  桥只能单向通行。
  两辆车从桥两端同时驶入 → 在桥中对峙
  → 都想前进 → 都让对方先退 → 谁也不退 → 永远卡住
  → 死锁！
  
  解决方法：一辆车倒退（资源抢占和回退）
```

```
进程访问资源的流程（三步）：
  ① 请求/获取 → ② 使用/占用 → ③ 释放

  资源类型举例：
    可重用资源：CPU时间、内存、I/O设备、文件、信号量
    消耗资源：中断、信号、消息
```

### 资源分配图

```
两类顶点：进程 P + 资源 R（R有实例数）
两类有向边：
  Pi → Rj  资源请求边：Pi 请求 Rj
  Rj → Pi  资源分配边：Rj 已分配给 Pi

示例：                         判定：
P1→R1→P2→R3→P3→R2→P1        有循环等待 → 死锁！
P1→R1→P2→R3→P3→R2→P1        
但 R2 还有一个实例被 P4 持有      → P4 释放 R2 后循环可打破
                                → 没有死锁
```

## 2. 死锁的四个必要条件

> 四个条件**必须同时满足**才可能死锁。

| # | 条件 | 含义 |
|:--:|------|------|
| ① | **互斥** | 任何时刻只能有一个进程使用一个资源实例 |
| ② | **持有并等待** | 进程保持至少一个资源，并正在等待获取其他进程持有的资源 |
| ③ | **非抢占** | 资源只能在进程使用后**自愿释放**，不能强行抢走 |
| ④ | **循环等待** | 存在等待链：P0→P1→P2→...→Pn→P0 |

```
打破四个条件中的任意一条 → 就能预防死锁
```

## 4. 死锁预防

> **打破四个必要条件之一**，确保死锁永远不发生。

| 打破条件 | 方法 | 缺点 |
|------|------|------|
| **互斥** | 把互斥资源封装成可同时访问 | 并非所有资源都能这样 |
| **持有并等待** | ① 进程开始时**一次申请所有**需要的资源<br>② 请求资源时不持有任何其他资源 | 资源利用率低，可能饥饿 |
| **非抢占** | 请求不能立即分配时，**释放已占有资源** | 实现复杂 |
| **循环等待** | 对资源**排序**，要求进程按顺序请求资源 | 需对所有资源编号 |

## 5. 死锁避免 — 银行家算法

> ⭐ **本章核心算法**。在分配资源前判断分配后是否**安全**，不安全则拒绝。

### 5.1 数据结构

```
n = 线程数，m = 资源类型数

Max[n×m]：        线程 Ti 最多需要 Rj 的 Max[i,j] 个实例（声明最大需求）
Available[m]：     当前有 Available[j] 个 Rj 可用
Allocation[n×m]：  Ti 已分配了 Allocation[i,j] 个 Rj
Need[n×m]：        Ti 未来还需要 Need[i,j] 个 Rj

关系：Need[i,j] = Max[i,j] - Allocation[i,j]
```

### 5.2 安全状态

```
安全序列 <P1, P2, ..., Pn> 满足：
  对每个 Pi，Pi 还需要的资源 ≤ 当前可用 + 所有 Pj(j<i) 持有的资源
  
  → Pi 可以完成 → 释放资源 → Pi+1 可以完成 → ... → 全部完成

安全状态 → 一定没有死锁
不安全状态 → 可能出现死锁

  死锁 ⊆ 不安全状态
```

### 5.3 银行家算法——资源请求判断

```
输入：线程Ti 请求资源向量 Requesti

步骤：

① 如果 Requesti ≤ Need[i]，继续。否则拒绝（超过声明最大需求）。

② 如果 Requesti ≤ Available，继续。否则 Ti 必须等待（资源不够）。

③ 假设分配，生成"试算环境"：
    Available' = Available - Requesti
    Allocation[i]' = Allocation[i] + Requesti
    Need[i]' = Need[i] - Requesti

④ 调用 安全状态判断算法（见 5.4）

⑤ 如果结果安全 → 真正分配资源给 Ti
   如果结果不安全 → 拒绝 Ti 的请求，Ti 阻塞等待
```

### 5.4 安全状态判断算法（核心）

```
输入：Available[m], Allocation[n×m], Need[n×m]

算法步骤：

① 初始化：
    Work = Available       （当前可用的资源）
    Finish[i] = false      （所有线程标记为"未完成"）

② 寻找满足条件的 Ti：
    (a) Finish[i] == false
    (b) Need[i] ≤ Work     ← Ti还需要的 ≤ 当前可用的
    
    如果找到 → 步骤③
    如果找不到 → 步骤④

③ 假装 Ti 执行完毕，回收它的资源：
    Work = Work + Allocation[i]   // Ti释放所有已占用的资源
    Finish[i] = true
    回到步骤②

④ 如果所有 Finish[i] == true → 系统安全 ✅
   如果存在 Finish[i] == false → 系统不安全 ❌（死锁风险）
```

### 5.5 银行家算法的特征

| 优点 | 缺点 |
|------|------|
| 避免死锁 | 需要预知**最大需求**（不现实） |
| 允许进程动态申请资源 | 进程数固定 |
| 比死锁预防更灵活 | 资源数固定 |

## 6. 死锁检测算法

> 允许死锁发生，定期检测。与银行家算法结构**几乎一样**，只是用的是 `Request` 而非 `Need`。

### 6.1 数据结构

```
Available[m]：       当前每种资源可用数量
Allocation[n×m]：    已分配矩阵
Request[n×m]：       当前请求矩阵（线程 Ti 正在请求的）
```

### 6.2 死锁检测算法

```
① 初始化：
    Work = Available
    对于所有 i：
      如果 Allocation[i] > 0 → Finish[i] = false
      否则 → Finish[i] = true（不占资源的线程视为已完成）

② 寻找满足条件的 Ti：
    (a) Finish[i] == false
    (b) Request[i] ≤ Work     ← Ti正在请求的 ≤ 当前可用的
    
    找到 → 步骤③；找不到 → 步骤④

③ 回收 Ti 的已分配资源：
    Work = Work + Allocation[i]
    Finish[i] = true
    回到步骤②

④ 如果存在 Finish[i] == false → 死锁存在！❌
   所有 Finish[i] == true → 没有死锁 ✅

复杂度：O(m × n²)（m=资源类型数，n=线程数）
```

#### 死锁检测 PPT 示例

```
3种资源：A(7), B(2), C(6)
5个线程：T0-T4

时刻 T0：

        Alloc      Request
      A  B  C     A  B  C
  T0   0  1  0    0  2  0
  T1   2  0  0    1  0  0
  T2   3  0  3    0  0  0
  T3   2  1  1    0  0  2
  T4   0  0  2    0  0  0

Alloc总计：A=7, B=2, C=6
Available = (7-7, 2-2, 6-6) = (0, 0, 0)

初始化：Work=(0,0,0), Finish=(f,f,f,f,f)
但 T0的Alloc=(0,1,0)≠0, T2的Alloc>0...

第1轮：
  T0: Req(0,2,0) ≤ Work(0,0,0)? ❌
  T1: Req(1,0,0) ≤ (0,0,0)? ❌
  T2: Req(0,0,0) ≤ (0,0,0)? ✅ → 回收！
  Work = (0,0,0) + (3,0,3) = (3,0,3)
  Finish[2] = T

第2轮：
  T0: Req(0,2,0) ≤ (3,0,3)? ... (0≤3?, 2≤0?) ❌
  T1: Req(1,0,0) ≤ (3,0,3)? ✅ → 回收！
  Work = (3,0,3) + (2,0,0) = (5,0,3)
  Finish[1] = T

第3轮：
  T0: Req(0,2,0) ≤ (5,0,3)? B=2 > 0 ❌
  T3: Req(0,0,2) ≤ (5,0,3)? ✅ → 回收！
  Work = (5,0,3) + (2,1,1) = (7,1,4)
  Finish[3] = T

第4轮：
  T0: Req(0,2,0) ≤ (7,1,4)? ✅ → 回收！
  Work = (7,1,4) + (0,1,0) = (7,2,4)
  Finish[0] = T

第5轮：
  T4: Alloc=(0,0,2)>0, Req=(0,0,0)≤(7,2,4)? ✅
  Finish[4] = T

全部 Finish = T → 没有死锁！✅
安全序列：<T2, T1, T3, T0, T4>

════ 如果 Request 变化... ════

假设 T1 的 Request 变为 (1,1,0)（增加了B的需求）：
  第1轮同 → 回收 T2 → Work=(3,0,3)
  第2轮：T1 Req(1,1,0) ≤ (3,0,3)? B=1 > 0 ❌
          T0 Req(0,2,0) ≤ (3,0,3)? ❌
          T3 Req(0,0,2) ≤ (3,0,3)? ✅ → 回收 T3 → Work=(5,1,4)
  第3轮：T0 B=2 > 1 ❌
          T1 B=1 > 1 ❌
          T4 回收 → Work=(5,1,6)
  第4轮：T0 B=2 > 1 ❌  T1 B=1 > 1 ❌
  
  → 找不到更多！T0,T1 的 Finish = false
  → 死锁存在！包括进程 T1,T2,T3,T4
```

### 6.3 检测算法 vs 银行家算法

```
                 银行家算法           死锁检测算法
                 ──────────          ──────────
比较条件：       Need[i] ≤ Work      Request[i] ≤ Work
何时使用：       分配资源前           定期或资源请求时
结果：          安全/不安全           死锁/无死锁
进程数：         固定                可变
*/

## 7. 死锁恢复

### 7.1 进程终止

```
① 终止所有死锁进程（最粗暴）

② 一次终止一个进程直到死锁消除
   终止顺序考虑：
   ● 进程优先级
   ● 进程已运行时间 + 还需运行时间
   ● 进程已占用资源
   ● 进程完成还需的资源
   ● 进程是交互还是批处理
```

### 7.2 资源抢占

```
① 选择被抢占进程 → 最小成本目标

② 进程回退 → 回退到安全状态，重启

③ 可能出现饥饿 → 同一个进程可能一直当"受害者"
```

## 8. 进程通信（IPC）

### 8.1 IPC 基本概念

```
IPC（Inter-Process Communication）：
  通信流程：
    ① 建立通信链路
    ② send(message) / receive(message) 交换消息
  
  链路特征：
    物理（共享内存、硬件总线）
    逻辑（逻辑属性）

通信方式分类：
  ├── 直接通信：send(P, msg) → 指定进程; receive(Q, msg) ← 指定对方
  └── 间接通信：send(QUEUE, msg) → 消息队列; receive(QUEUE, msg)
```

### 8.2 阻塞 vs 非阻塞通信

| | 阻塞（同步） | 非阻塞（异步） |
|------|------|------|
| **发送** | 发送后等待，直到接收者收到 | 发送后立即继续 |
| **接收** | 等待直到收到消息 | 请求后立即返回（可能收不到） |

### 8.3 四种 IPC 机制

```
┌──────────┬────────────────────────────────────────────┐
│  机制     │  特点                                       │
├──────────┼────────────────────────────────────────────┤
│ 信号      │ 进程间软件中断通知，信息量小（只有一个信号类型）     │
│ Signal   │ SIGKILL, SIGSTOP, SIGCONT...                │
│          │ 处理：捕获/忽略/屏蔽                           │
├──────────┼────────────────────────────────────────────┤
│ 管道      │ 进程间基于 内存文件 的通信                      │
│ Pipe     │ pipe(rgfd) → rgfd[0]读端, rgfd[1]写端       │
│          │ ls | more → shell创建管道连接两个进程          │
├──────────┼────────────────────────────────────────────┤
│ 消息队列   │ OS维护的以字节序列为单位的间接通信              │
│ MessageQ │ msgget→msgsnd→msgrcv→msgctl                │
│          │ 按FIFO顺序，相同标识的消息组成队列               │
├──────────┼────────────────────────────────────────────┤
│ 共享内存   │ 同一物理内存映射到多个进程地址空间               │
│ Shared   │ 最快！无系统调用、无数据复制                     │
│ Memory   │ shmget→shmat→shmdt→shmctl                  │
│          │ 需程序员自己同步（信号量配合）                    │
└──────────┴────────────────────────────────────────────┘
```

## 9. 知识脉络图

```
死锁
├── 定义：永远相互等待
├── 必要条件：互斥 + 持有等待 + 非抢占 + 循环等待
│
├── 处理方法
│   │
│   ├── 预防（破坏必要条件之一）
│   │   ├── 破坏互斥：资源封装为可共享
│   │   ├── 破坏持有等待：一次申请所有 / 不持有资源时申请
│   │   ├── 破坏非抢占：请求失败释放已占有
│   │   └── 破坏循环等待：对资源排序
│   │
│   ├── 避免——银行家算法 ⭐
│   │   ├── 数据结构：Max/Alloc/Need/Available
│   │   ├── 安全状态判断：Need ≤ Work 则回收
│   │   │   Work = Work + Alloc[i]; Finish[i]=T
│   │   │   全部 Finish=T → 安全 ✅
│   │   └── 请求判断：试分配 → 安全判断 → 安全才真分配
│   │       O(m×n²)
│   │
│   └── 检测+恢复
│       ├── 检测算法：与银行家几乎一样，用Request代替Need
│       │   存在Finish=F → 死锁！
│       └── 恢复：终止进程 / 资源抢占+回退
│
└── 大多数OS选择：忽略死锁（让应用自己处理）
