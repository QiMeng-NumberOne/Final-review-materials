## 1. 背景：为什么需要同步

### 1.1 独立进程 vs 并发进程

```
独立进程：                         并发进程 + 共享资源：
  不和其他进程共享资源                  多个进程读写同一块内存/文件/变量
  确定性：输入决定结果                  不确定性：执行顺序不确定
  可重现：能重现起始条件                不可重现：bug 间歇性出现 ← 最难调试！
```

### 1.2 并发执行的三个好处

```
① 共享资源
  多个用户使用同一台计算机、银行账号在多台ATM操作

② 加速
  I/O 和 CPU 计算可重叠（并行）
  程序划分成多个模块在多个处理器上并行执行

③ 模块化
  将大程序分解成小程序 → 易于复用和扩展
  以编译为例：gcc → cpp → cc1 → cc2 → as → ld
```

### 1.3 并发时的典型错误

```c
// 内核分配新进程ID：new_pid = next_pid++;
// 一行C代码 → 三条机器指令：

LOAD  next_pid, Reg1      // ① 读取 next_pid
STORE Reg1, new_pid       // ② 存为 new_pid（这就是返回的ID）
INC   Reg1                // ③ next_pid 加1
STORE Reg1, next_pid      // ④ 写回

两个进程并发执行时的交错：

进程A: LOAD next_pid(100) → STORE new_pid(100) →  ... → INC(101) → STORE → ...
进程B:               LOAD next_pid(100) → STORE new_pid(100) → ...

  A 和 B 都读到了 100 → 都得到了 PID=100 → 两个进程同一个 PID！
```

### 1.4 进程的交互关系

```
┌──────────────┬──────────────────────┬──────────────────────┐
│  相互感知程度  │      交互关系          │      进程间影响        │
├──────────────┼──────────────────────┼──────────────────────┤
│ 相互不感知    │ 独立                  │ 互不影响              │
│ 间接感知      │ 通过共享进行协作        │ 互斥 / 死锁 / 饥饿    │
│ 直接感知      │ 通过通信进行协作        │ 依赖对方信息          │
└──────────────┴──────────────────────┴──────────────────────┘

间接感知时可能产生的问题：
  互斥 (Mutual Exclusion)
    → 一个进程占用资源，其他进程不能用
    
  死锁 (Deadlock)
    → 多个进程各占用部分资源，形成循环等待
    
  饥饿 (Starvation)
    → 一个进程一直得不到资源（其他进程轮流占用）
```

## 2. 现实生活中的同步问题 — 买面包案例

PPT 用"两个人买面包"的案例层层递进，引出临界区的同步问题。

```
场景：冰箱没面包了，A和B各自决定要不要去买

时间线：
  A: 3:00  查看冰箱 → 没有面包
     3:05  离开家去商店
  B: 3:10  查看冰箱 → 没有面包（A还没回来）
     3:15  离开家去商店
     3:20  买面包回家
  A: 3:25  买面包回家

结果：买了 两份 面包 → 浪费！

问题根源：检查面包和去买面包 不是原子操作！
```

### 方案一：用便签标记（检查后留签）

```
A: if (nobread) {          B: if (nobread) {
     if (noNote) {              if (noNote) {
       leave Note;                leave Note;     ← A检查了noNote后才留签
       buy bread;                 buy bread;      ← 这中间B也检查了noNote
       remove Note;               remove Note;
     }                          }
   }                          }

问题：A检查便签(无) → 还没留 → B也检查(无) → 两人都留 → 都去买
     bug 间歇性出现 → 极难调试！
```

### 方案二：先留便签再检查

```
A: leave Note;             B: leave Note;        ← 都先留了便签
   if (nobread) {             if (nobread) {
     if (noNote) {              if (noNote) {    ← 都看到对方有便签
       buy bread;                 buy bread;
     }                          }
   }                          }
   remove Note;                remove Note;

问题：两人都留了便签 → 都看到对方有 → 都不买 → 饿死！
     产生 死锁 的雏形
```

### 方案三：给便签加标记（区分A和B）

```
A: leave note_A;           B: leave note_B;
   if (no note_B) {           if (no note_A) {
     if (nobread) {              if (nobread) {
       buy bread;                  buy bread;
     }                          }
   }                          }
   remove note_A;              remove note_B;

问题：A留note_A后看到没有note_B → 认为B不会买
     B留note_B后看到没有note_A → 认为A不会买
     → 两人都"放心了"，都不买！
```

### 方案四：两个人用不同的流程（有效但丑陋）

```
A: leave note_A;              B: leave note_B;
   while(note_B) {               if (no note_A) {
     do nothing;   // 忙等          if (nobread) {
   }                                 buy bread;
   if (nobread) {                  }
     buy bread;                   }
   }                              remove note_B;
   remove note_A;

枚举所有可能 → 确认有效！ ✅

但：
  ● A和B代码不同 → 不可推广
  ● A在忙等 → 浪费CPU
  ● 超过2个人怎么办？
```

**启示**：买面包问题 → 临界区同步问题

```
买面包问题                          临界区同步
──────────                         ──────────
面包数量         ←→       共享变量
只有一人去买      ←→       互斥
便签             ←→       锁 / 标志位
```

## 3. 临界区（Critical Section）

### 3.1 定义

> 临界区 = 进程中**访问临界资源**的一段需要**互斥执行**的代码。

```
线程 Ti 的代码结构：

    do {
        ┌──────────────────┐
        │ enter section    │ ← 进入区：检查可否进入，设置"正在访问"标志
        ├──────────────────┤
        │ critical section │ ← 临界区：访问共享资源的代码，必须互斥！
        ├──────────────────┤
        │ exit section     │ ← 退出区：清除"正在访问"标志
        ├──────────────────┤
        │remainder section │ ← 剩余区：其他不涉及共享资源的代码
        └──────────────────┘
    } while (1);
```

### 3.2 临界区的四条访问规则

| 规则 | 含义 | 要求 |
|------|------|:--:|
| **空闲则入** | 没有进程在临界区时，任何进程可进入 | 必须 |
| **忙则等待** | 有进程在临界区时，其他进程均不能进入 | 必须 |
| **有限等待** | 等待进入的进程不能无限期等待（不能饿死） | 必须 |
| **让权等待（可选）** | 不能进入临界区的进程应释放CPU（阻塞而非忙等） | 可选 |

## 4. 方法1：禁用硬件中断

```
思路：没有中断 → 没有上下文切换 → 没有并发

local_irq_save(flags);       // ① 关中断 + 保存中断标志
    critical section          // ② 执行临界区（没人能打断）
local_irq_restore(flags);    // ③ 恢复中断

原理：中断是上下文切换的触发器，
     关了中断 = 当前进程独占CPU = 不会有人来竞争
```

| 优点 | 缺点 |
|------|------|
| 简单 | 整个系统停止（中断全关） |
| | 可能导致其他进程饥饿 |
| | 临界区长时 → 硬件中断丢失 |
| | **仅限单处理器**（多处理器关本CPU中断不影响其他CPU） |

## 5. 方法2：基于软件的解决方法

### 5.1 第一次尝试：turn 变量

```c
int turn = 0;   // turn==i 表示允许Ti进入临界区

// 线程 Ti
do {
    while (turn != i) ;    // 忙等，直到轮到自己
    critical section
    turn = j;              // 轮到对方
    remainder section
} while (1);
```

| 判定 | 结果 |
|------|:--:|
| 忙则等待 | ✅ |
| 空闲则入 | ❌ Ti不在临界区，Tj想进去，但turn还指向Ti → Tj必须等Ti先进一次 |

### 5.2 第二次尝试：flag 变量 v1

```c
int flag[2] = {0, 0};  // flag[i]==1 表示Ti 在临界区内

// 线程 Ti
do {
    while (flag[j] == 1) ;   // 等对方离开
    flag[i] = 1;             // 标记自己进入
    critical section
    flag[i] = 0;             // 标记离开
    remainder section
} while (1);
```

| 判定 | 结果 |
|------|:--:|
| 忙则等待 | ❌ 两人同时看到flag[j]==0 → 都进入 → 同时进了临界区！ |

### 5.3 第三次尝试：flag 变量 v2

```c
int flag[2] = {0, 0};  // flag[i]==1 表示Ti 想要 进入临界区

// 线程 Ti
do {
    flag[i] = 1;             // 先声明"我要进去"
    while (flag[j] == 1) ;   // 等对方放弃
    critical section
    flag[i] = 0;
    remainder section
} while (1);
```

| 判定 | 结果 |
|------|:--:|
| 忙则等待 | ✅ |
| 空闲则入 | ❌ 两人都声明了flag=1 → 都在while中等对方 → **死锁** |

### 5.4 Peterson 算法（1981）⭐

> 两线程互斥的经典软件解决方案。两个线程共用 `flag[2]` 和 `turn`。

```c
int turn;                // 该谁进入
boolean flag[2];          // flag[i]==true 表示Ti 准备好了

// 线程 Ti 的代码
do {
    flag[i] = true;                  // ① "我准备好了"
    turn = j;                        // ②  谦让：让对方先走
    while (flag[j] && turn == j);    // ③  如果对方准备好了 且 轮到对方 → 等待
    
    critical section
    
    flag[i] = false;                 // ④  离开临界区
    remainder section
} while (1);
```

**正确性分析**：

```
关键：turn = j （谦让机制）

  Ti 和 Tj 同时想进 → 都设 flag=true
  → 都写 turn：Ti写 turn=j，Tj写 turn=i
  → turn 最后的值只有一个！← 硬件保证
  → 假设最后是 turn=j → Ti 在 while 中等待，Tj 跳过 while 进入临界区
  → 互斥成功！✅

四条规则检查：
  ✅ 空闲则入：对方 flag=false → 直接跳过 while
  ✅ 忙则等待：双方 flag=true → turn 决定谁进
  ✅ 有限等待：对方退出后 flag=false → 自己马上能进
  ❌ 让权等待：while 中是忙等（一直在循环）
```

| 优点 | 缺点 |
|------|------|
| 正确实现了两线程互斥 | 忙等待（浪费CPU） |
| 仅需两个共享变量 | **仅适用于两个线程** |

### 5.5 Dekker 算法

```c
flag[0] = false; flag[1] = false;
turn = 0;  // 或 1

// 线程 Ti
do {
    flag[i] = true;
    while (flag[j] == true) {
        if (turn != i) {             // 不是我的轮次
            flag[i] = false;          // 主动放弃声明
            while (turn != i) { }     // 等轮到我
            flag[i] = true;           // 重新声明
        }
    }
    
    critical section
    turn = j;                         // 轮次给对方
    flag[i] = false;
    remainder section
} while (1);
```

**与 Peterson 的区别**：

```
Dekker：不是自己轮次时 → 主动 放弃 flag → 让对方进
Peterson：不放弃 flag，用 turn 的 最后写入 机制解决 → 更简洁
```

---

### 5.6 N 线程：Eisenberg & McGuire 算法

```
思想：线程排成环状
  Ti 进入前 → 等待从 turn 到 i-1 的所有线程都退出临界区
  Ti 退出时 → 把 turn 改成下一个申请线程

适用于 N 个线程 → 但复杂度随 N 急剧增长
```

### 5.7 软件方法的共同缺陷

```
● 复杂：需要共享数据项，代码易出错
● 忙等待：浪费 CPU 时间
● 可扩展性差：超过两个线程后极其复杂
● 需要程序员自己实现，容易犯错
```

## 6. 方法3：更高级的抽象方法

> 硬件提供**原子操作指令**，操作系统在此基础上构建**锁、信号量**等高层抽象。

### 6.1 原子操作指令

> **原子操作** = 一次不存在任何中断或失败的操作。要么全部完成，要么根本没做。

**Test-and-Set（TS 指令）**：

```c
// 硬件保证以下三步是 原子的 —— 不可被中断或分割
boolean TestAndSet(boolean *target) {
    boolean rv = *target;     // ① 读取旧值
    *target = true;           // ② 设置为1
    return rv;                // ③ 返回旧值
}
```

**Exchange（交换指令）**：

```c
// 原子地交换两个内存单元的值
void Exchange(boolean *a, boolean *b) {
    boolean temp = *a;
    *a = *b;
    *b = temp;
}
```

---

### 6.2 锁（Lock）

> 锁是一个**抽象的数据结构**。一个二进制变量（锁定/解锁），加上等待队列。

```c
class Lock {
    int value = 0;         // 0=空闲, 1=被占用
    WaitQueue q;           // 等待此锁的线程队列
};

Lock::Acquire()    → 获得锁（如果忙则等待）
Lock::Release()    → 释放锁，唤醒等待的线程
```

**使用锁保护临界区**：

```c
lock->Acquire();
    new_pid = next_pid++;    // ← 临界区，互斥执行
lock->Release();
```

---

### 6.3 自旋锁（Spinlock）

> 忙等待锁：拿不到锁就在原地循环（spin），不释放 CPU。

```c
class Lock {
    int value = 0;   // 0=空闲, 1=忙
};

Lock::Acquire() {
    while (TestAndSet(&value))   // TS 原子操作
        ;  // spin! 一直循环，消耗CPU
}

Lock::Release() {
    value = 0;
}
```

**TS 指令如何实现自旋锁**：

```
value=0（锁空闲）：
  TS(0) → 返回 0（旧值），同时 value 被设为 1
  → while(0) 不成立 → 跳出循环 → 获得了锁！

value=1（锁被占用）：
  TS(1) → 返回 1（旧值），value 保持为 1
  → while(1) 成立 → 继续循环 → 忙等 ✳
```

| 优点 | 缺点 |
|------|------|
| 适用于单处理器或共享主存多处理器 | **忙等待**浪费 CPU |
| 简单且容易证明 | 可能导致**饥饿**（离开时多等进程只有一个能拿到） |
| 支持多临界区 | 低优先级持锁 + 高优先级等锁 → **死锁风险** |

---

### 6.4 无忙等待锁

> 拿不到锁时不忙等，而是**主动让出 CPU**（进入阻塞态）。

```c
class Lock {
    int value = 0;
    WaitQueue q;     // 等待队列
};

Lock::Acquire() {
    while (TestAndSet(&value)) {
        // 没拿到锁 → 不忙等！
        add current TCB to wait queue q;    // 把自己加入等待队列
        schedule();                         // 主动让出CPU！
    }
}

Lock::Release() {
    value = 0;
    remove one thread t from q;             // 从等待队列取出一个线程
    wakeup(t);                              // 唤醒它
}
```

```
忙等待锁 vs 无忙等待锁：

  自旋锁（忙等）：while(TS) ;  ← 占着 CPU 空转
  无忙等锁：      while(TS) { 入队; schedule(); }  ← 让出 CPU ✅

  无忙等待 = 实现了"让权等待"（临界区第四条规则）
```

## 7. 三种同步方法对比总结

| | 禁用中断 | 软件方法 | 高层抽象（锁） |
|------|:---:|:---:|:---:|
| **并发级别** | 低 | 中 | **高** |
| **性能** | 好 | 差（忙等） | **好** |
| **复杂度** | 简单 | 复杂 | 简单（使用者视角） |
| **适用场景** | 单CPU，极短临界区 | 少量线程，无硬件支持 | **主流方案** |
| **让权等待** | 否 | 否（忙等） | 可支持（无忙等锁） |
| **多处理器** | 不支持 | 支持（但需原子指令） | 支持 |

**同步方法选用原则**：

```
禁用中断 → 软件方法 → 高层抽象

硬件提供原子操作 → 构建锁 → 程序员使用锁

Lock 是高级同步抽象：
  ● 互斥可使用锁来实现
  ● 需要硬件支持（原子指令）
  ● 操作系统在此基础上构建更高级的同步原语（信号量、条件变量...）
```

## 8. FAQ

### Q1：为什么独立进程没问题，并发进程就有问题？

独立进程不共享资源 → 输入决定输出 → **确定性**。并发进程共享资源 → 执行顺序不确定 → 结果不可预测 → bug **间歇性**出现，最难调试。

### Q2：临界区的四条规则是什么？

**空闲则入**（没人在时能进）、**忙则等待**（有人在时不能进）、**有限等待**（不能饿死）、**让权等待**（进不去时应释放CPU，可选）。

### Q3：Peterson 算法的核心技巧是什么？

`turn = j` 的**谦让机制**。两人同时写 `turn` → 硬件保证最后只有一个值留下 → 写 `turn=j` 的人让写 `turn=i` 的人先进 → 互斥成立。

### Q4：自旋锁和无忙等待锁的区别？

- **自旋锁**：拿不到锁时 `while(TS)` 一直循环 → 忙等，浪费CPU但适合极短临界区
- **无忙等待锁**：拿不到锁时 `入等待队列 + schedule()` → 让出CPU，适合临界区较长的情况

### Q5：为什么禁用中断只适用于单处理器？

多处理器中，关本CPU的中断不影响其他CPU。其他CPU上的进程仍然可能同时访问共享资源。

### Q6：锁的特征（优缺点）？

优点：适用于多处理器、支持任意数量进程、简单易证明、支持多临界区。
缺点：忙等待浪费CPU、可能导致饥饿、含锁的低优先级进程可能阻塞高优先级进程。

## 9. 知识脉络图

```
并发 + 共享资源 → 不确定性、间歇性bug
        │
        ▼
    临界区 (Critical Section)
    ├── 进入区 → 临界区 → 退出区 → 剩余区
    └── 四条规则：空闲则入 / 忙则等待 / 有限等待 / 让权等待
        │
        ▼
    三种实现方法
        │
        ├── ① 禁用中断
        │   └── 关中断→临界区→开中断（仅单CPU，简单但粗暴）
        │
        ├── ② 软件方法
        │   ├── turn变量 → 不满足空闲则入
        │   ├── flag v1 → 不满足忙则等待
        │   ├── flag v2 → 死锁
        │   ├── Peterson → ✅ 两线程经典解（忙等）
        │   ├── Dekker → 更复杂的两线程解
        │   └── Eisenberg&McGuire → N线程（极复杂）
        │
        └── ③ 高层抽象 ← 主流
            ├── 硬件原子指令：Test-and-Set、Exchange
            ├── 自旋锁：while(TS) 忙等
            │   └── 适合极短临界区
            └── 无忙等锁：入等待队列 + schedule()
                └── 实现了让权等待

买面包案例贯穿整章：
  方案一二三的失败 → 方案四复杂但有效
  → 对应软件方法的逐步改进
  → 最终需要高层抽象（锁）来解决
```
